## 决策账本（Grill 结果）

### 已确认

| 项 | 决定 |
|----|------|
| 问题本质 | Brief 玩家可见信息不够全（界面/流程/呈现/需要哪些参数），不是 API 温度 alone，也不是定死 schema |
| 数值 vs 参数名 | **具体数值**可进 production/`tuning`；**需要哪些参数/表（名与含义、出现在哪）**应出现在 brief（由补全/头脑风暴写出，非固定键表） |
| 禁止 | 通用必填 `screens[]` / `tuning_needs[]` 等「每个游戏都要有」的死 schema |
| 手段组合 | **A+B+C+D 可一起**：略高/可配 temperature、定向补全、内部多轮自对话、Critic 观感门禁；文字成本可接受 |
| 补全触发 | **可选按钮**（非导出自动）；可带用户要求 **二次/多次**补全 |
| 头脑风暴 | 针对**某一议题**；多视角并行 → **先吵后拣** → 再写回 `draft_brief` |
| 并行实现 | **v1：同模型多角色**；**可选：多模型并行**（配置允许时） |
| 资产 | 写回 draft 时 **同时提议候选 `assets[]` 行**（可改可删） |
| 与 PM | 不把「游戏长什么样」的权威补全放到项目经理/production；PM 仍订数值与施工 |

### 已排除

| 项 | 原因 |
|----|------|
| 导出前强制跑满补全 | 用户改为按钮可控 |
| 固定品类必填字段表 | 每款游戏不同，无法定死 |
| 单靠调高 temperature | 发散≠系统完备；仅作辅旋钮 |
| 头脑风暴自动融合不经挑选 | 用户要先拣方案 |
| 补全只改文字不动 assets | 易再导致图视频返工 |

### 默认建议（写入 Spec，未单独投票则按此）

| 项 | 默认 |
|----|------|
| Critic | 补全/采用后**可再跑** makeability；导出门闩规则保持（intent 挡、detail 不挡）；Critic **不**替代补全按钮 |
| 过程可见 | 补全/头脑风暴有进度与摘要；完整轮次可展开，默认不刷屏 |
| 温度 | 补全中等；头脑风暴角色稿可略高；均可配置，不当事主手段 |

## 背景输入

读 brief 应能大致想象游戏：有菜单则知有什么、顺序、点击效果；有拉线则知张力/线等信息如何呈现、在哪。  
现网：策划薄 Chat → draft → makeability → export；细节易停在浅句或被标 detail 丢到 production，资产表与「看得见的东西」脱节。

## 工程理解

Foundry 以 **`draft_brief` / `brief.json` 为玩法与资产契约**；production 承载施工与数值。  
完备性应靠 **LLM 按本局内容开放式加厚** + **议题多视角吵架**，再经用户确认写回；不是通用字段清单。

## 目标

1. **补全按钮**：对当前 `draft_brief` 跑内部补全（可含自对话多轮 + 可配 temperature）→ 合并加厚 draft（含所需参数名/呈现描述 + 候选资产）。
2. **二次补全**：用户可带自然语言要求再跑（「只补 HUD」「张力再具体点」）。
3. **议题头脑风暴**：用户给议题 → v1 多角色并行（可选多模型）→ 方案对比 → 采用/融合 → 写回 draft（含相关资产候选）。
4. **与导出解耦**：不自动在 export 前跑补全/头脑风暴；export 仍走现有 makeability 门闩。
5. **不定死 schema**：允许本局自描述结构出现在 draft；校验/Critic 以「能否想象出游戏 / 开放缺口」为主，不以固定键齐备为门禁。

## 非目标

- 通用必填 UI schema / 全品类参数字典
- 导出强制自动补全
- 用 temperature 替代补全任务设计
- PM 改 brief 意图（v1 仍禁止）
- 补全环直接触发 pipeline / 生图
- v1 必须真·多厂商同时在线（多为可选增强）

## 当前架构约束

- 策划：`brief chat` / host-chat 会话与 `draft_brief`
- Makeability Critic：独立子调用；`intent_gaps` / `detail_gaps`
- GUI：Docs 侧栏看 draft；导出按钮已有
- Provider：角色可配模型；多模型并行依赖已配置账号
- 资产：`assets[]` 驱动 pipeline

## 方案选择

**采用：按钮驱动的 Brief 加厚流水线 + 议题多视角头脑风暴（先拣后写）+ 写回时附带资产候选；A/B/C/D 组合；无通用必填字段表。**

```text
[补全细节] --(可选 user hint)--> 自对话/补全 LLM(s) --> merge draft (+ assets 候选)
                                      --> 可选再跑 Critic

[议题头脑风暴] --> 多角色(±多模型)并行 --> 方案卡 --> 用户采用/融合 --> merge draft (+ assets)
```

## 被排除方案

| 方案 | 原因 |
|------|------|
| 固定 `screens`/`tuning_needs` 必填 | 用户否决 |
| 导出挂钩自动补全 | 用户要按钮与可重复 |
| 头脑风暴自动写入 | 要先吵后拣 |
| 只生产、不碰 assets | 图视频返工 |

## 边界与失败模式

| 模式 | 处理 |
|------|------|
| 补全跑飞 / 矛盾 | 合并前校验 JSON；失败保留旧 draft 并报错；支持只接受部分 diff（若实现成本高可 v1 整稿替换+撤销） |
| 用户不满意 | 带要求再点补全；或议题头脑风暴深挖一点 |
| 多模型未配置 | 降级仅多角色；UI 标明 |
| 候选资产过多 | 去重 by name；标 provisional；用户可删 |
| 与 makeability 冲突 | 写回后 intent 仍挡导出；引导再补全或手改 |

## 显式假设

- 用户接受补全/头脑风暴的文字 Token 成本。
- v1 同模型多角色已能明显减轻「建议单薄」。
- 不引入全游戏统一 UI 字段表仍能靠提示词与 Critic 提升完备度。

## 领域语言

| 术语 | 含义 |
|------|------|
| **补全（enrich）** | 按钮触发的整稿加厚（可含自对话） |
| **议题头脑风暴** | 针对单点议题的多视角并行方案生成 |
| **先吵后拣** | 先出多案，用户采用/融合后再写 draft |
| **参数名清单** | brief 中声明需要哪些数值/表（可无具体数） |
| **资产候选** | 写回时提议的 `assets[]` 行，可改删 |

## 功能需求

### FR-1 补全按钮

- GUI 策划侧提供「补全细节」（文案可调）
- 可选文本：本轮补全要求
- 调用 CLI/IPC：读 session draft → 补全流水线 → 写回 session `draft_brief`
- 支持重复执行；后轮尊重用户要求（增量/聚焦）

### FR-2 补全流水线内容

- 含：内部自对话或等价多步（C）、定向合并（B）、可配 temperature（A）
- 输出必须尽量覆盖：玩家可见流程/界面呈现、**需要哪些参数及其呈现位置**（无数也可）、相关资产候选
- **禁止**依赖「全游戏固定字段是否填齐」作为成功标准

### FR-3 议题头脑风暴

- 输入：议题文本 + 可选约束
- v1：≥3 角色并行（同 provider/模型）
- 可选：多模型各出稿（需配置）
- 输出：方案列表（标题、要点、取舍）供 UI 展示
- 用户「采用」或「融合所选」→ 合并进 draft（+ 资产候选）

### FR-4 写回与资产

- 合并后侧栏可见变厚 draft
- 新/改资产行可识别（如 provisional 标记或合并报告）
- 不自动 export、不自动 pipeline

### FR-5 Critic 关系

- 不替代 makeability；导出规则不变
- 补全/采用后可提示或提供「再审查」；不强制与补全按钮绑死同一次点击（实现可一并提供）

### FR-6 文档

- AI-HANDOFF / HOST-CHAT：补全与头脑风暴入口、与 production 数值分工、不定死 schema

## 非功能需求

- 并行角色调用应并发，总等待可接受（文字成本优先于延迟也可串行降级）
- 失败可重试；不损坏 session 文件
- 可配置 temperature / 角色数（有合理默认）

## 安全关注点

- 仅写当前 session draft，不写任意路径
- 不把 API Key 打进 brief
- 用户内容进提示词按现有 LLM 边界处理

## 成功标准

1. 粗 draft → 点补全 → 侧栏可看出菜单/主循环呈现等明显变厚；并出现相关资产候选或明确「无需贴图」说明。  
2. 带要求二次补全，只加深指定议题而非整稿无控膨胀（允许轻度关联扩写）。  
3. 议题头脑风暴出 ≥3 可辨别方案；采用后 draft 含该呈现，且可含资产候选。  
4. 未点补全仍可按旧路径 export（仍受 makeability 约束）。  
5. 无「缺少固定 screens 字段」类硬校验；旧 brief 不因缺新键无法打开。

## PR Review 关注点

- 是否又引入通用必填 schema
- 写回是否可回滚/失败安全
- 资产候选是否过度灌水
- 多模型关闭时是否干净降级
- 是否误在 export 自动触发
